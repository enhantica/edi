## Ask a question

Use the [edi issue tracker](https://github.com/enhantica/edi/issues) for questions about the current product, unexpected behaviour and feature proposals. Say whether you are using the browser app, desktop app, Python or Command Line, and identify the version or source commit when you can.

For a usage question, describe the scientific task and the step where you got stuck. Linking the documentation page or example you followed helps distinguish an unclear instruction from a software problem.

## Report a problem

A useful report includes:

- what you expected to happen and what happened instead;
- the interface, operating system and browser where relevant;
- the smallest project or input that reproduces the problem;
- the steps or commands needed to reach it;
- the full error message and any relevant application Messages.

Remove unpublished or confidential data before attaching a project to a public issue. A reduced example is often easier to investigate than a complete experimental campaign.

## Suggest an improvement

Explain the task the change would help you complete. Include the present workaround, the interface you use and an example of the desired result. For documentation, name the page and the point where its explanation stopped being clear.

## Contribute

The current source is in [enhantica/edi](https://github.com/enhantica/edi). Build, architecture and testing information belongs in the separate [contributor documentation](https://enhantica.github.io/edi/dev/).

For a change to scientific behaviour, include the relevant reference and a reproducible case. For a documentation change, check commands and screenshots against the interface and software version being documented.

## Keep the analysis reproducible

When a discussion leads to a result you plan to share, keep its inputs, settings and software identity. See [citing and recording an analysis](citation.md).
